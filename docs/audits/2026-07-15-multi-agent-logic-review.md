## 维度：dedup + hashing subsystem correctness

> The core of the subsystem is well-built: scanner/_hashing.py's stable hash is genuinely order-independent (per-file digests sorted before combining), the legacy variant is retained and accepted everywhere lookups happen, notes emit both hashes in frontmatter when they differ, and DedupIndex cleanly layers ledger + vault-scan recovery with crash-atomic (tmp+os.replace) writes; the service-side duplicate of the hash algorithm matches, and the __nonexistent_vault__ sentinel is benign on all OSes. The fragility is all at the edges: the worker writes its ledger to a different file than the batch prefilter and every maintenance tool reads (with a gitignore/privacy hole on the real path), the legacy→stable migration script crashes on import from a missing `import os`, the ledger's read-modify-write append loses entries under the batch scanner's own 3-way subprocess fan-out, and verify_and_clean/backfill_hash operate on stale assumptions (stable-only hashes, flat top-level vault) that make --clean destructive for legacy-era or folder-organized vaults.

### [HIGH] DedupIndex.append is a read-modify-write with no cross-process lock; the batch scanner's 3-worker subprocess fan-out can silently drop ledger entries

- 位置：`scanner/dedup_index.py:273`
- 状态：✅ 已确认（双票通过对抗验证）
- 细节：append() does `existing = history_path.read_text(...)` (line 273) then writes existing+hash to a tmp file and `os.replace`s it (line 287). os.replace makes each write atomic against crashes but not against concurrent writers: two processes that both read revision N each write their own N+1, and the second replace erases the first writer's hash. The class docstring even states "the pipeline is single-process, single-writer" — but zotero_batch_scanner.py:702-708 runs `ThreadPoolExecutor(max_workers=3)` spawning concurrent gemini_analyze_pdf.py subprocesses, each of which appends to the same ledger at gemini_analyze_pdf.py:1655 (dedup-hit canonicalize) and :1796 (post-success). Concrete failure: a >5-paper `--publish-target canary` batch (vault scan disabled, ledger is the only dedup layer) where two workers finish within the same read-to-replace window — one paper's hash is lost, and the next batch run re-processes that paper end-to-end, re-spending API tokens. The :1655 path is worse: groups that prefilter missed (e.g. parent-key-only matches, which prefilter_pdf_groups never checks) all dedup-hit within milliseconds of subprocess start, making concurrent lost updates likely rather than rare.

## 维度：retrieval service layer

> The service is mostly well-structured (env-driven config, localhost-only default binding, is_path_within_root helper, per-note/YAML try-excepts that avoid mid-run crashes), but two guard mechanisms are silently broken on the project's own pinned stack: /health raises TypeError and returns HTTP 500 on every call because a pathlib.Path is put into the jsonify payload, and detect_dim_mismatch always returns 'no mismatch' because `not embeddings` throws on the numpy ndarray that chromadb 1.5.5's peek() returns and the error is swallowed — so the advertised dimension-mismatch safety net never fires. The query-log write path is the weakest spot for filesystem safety: query_title is sanitized but workflow_id/short_id are not, and the new-file write skips the is_path_within_root check that other branches use, allowing writes outside QUERY_LOG_ROOT (localhost-only, so limited blast radius). Ledger logic diverges between builders: build_pdf_db keys on content hash (correct) while build_notes_db keys on filename, so edited notes are never re-embedded; build_pdf_db also marks a group complete when only some of its files ingested. All findings were verified by executing against the localrag venv (chromadb 1.5.5) or by direct reading; each cites file+line with a concrete failure scenario.

### [HIGH] /health returns HTTP 500 on every request because CHROMA_PATH (a pathlib.Path) is placed into the jsonify payload and is not JSON-serializable

- 位置：`service/query_server.py:553`
- 状态：✅ 已确认（双票通过对抗验证）
- 细节：Line 553 sets `"path": CHROMA_PATH` where CHROMA_PATH is a pathlib.Path (config.py line 75). Flask's jsonify calls json.dumps on the whole status dict, which raises `TypeError: Object of type WindowsPath is not JSON serializable`, so Flask returns a 500 HTML error page. Verified by running the app with the localrag venv: `GET /health` -> status 500, body `<!doctype html>...500 Internal Server Error`. This is independent of the SKIP flag and of readiness — CHROMA_PATH is always a Path, so /health NEVER returns the documented 200/503 JSON. Every skill or operator that polls /health to check readiness (search-* skills document doing exactly this) will always see failure. Fix: `str(CHROMA_PATH)`.

### [HIGH] detect_dim_mismatch never fires on the pinned chromadb 1.5.5 because `if not embeddings` raises on a numpy ndarray and is swallowed, defeating the entire dimension-mismatch guard

- 位置：`service/embedding_client.py:231`
- 状态：✅ 已确认（双票通过对抗验证）
- 细节：collection.peek() in chromadb 1.5.5 returns embeddings as a numpy.ndarray, not a list. Line 231 `if not embeddings or len(embeddings) == 0 or embeddings[0] is None:` evaluates `not <ndarray>`, which raises `ValueError: The truth value of an array with more than one element is ambiguous`. That ValueError is caught by the `except Exception as exc: return False, f"could not read stored embedding dim: {exc}"` on line 235, so the function ALWAYS returns (False, ...). Verified empirically: stored a 3-dim vector, monkeypatched get_embedding to produce 999-dim, called detect_dim_mismatch -> returned mismatch=False with message 'could not read stored embedding dim: The truth value of an array...'. Consequence: the startup guard the module docstring/comments advertise as catching the #1 silent foot-gun (user changes OLLAMA_EMBED_MODEL/EMBED_PROVIDER without rebuilding) is dead code — no INIT WARN, no _dim_warnings, so /health's 503-on-mismatch branch (query_server.py line 583-591) also never triggers. Fix: guard with `embeddings is None or len(embeddings) == 0` instead of `not embeddings`.

### [MEDIUM] Notes ledger is keyed on filename, so a note edited in place (same filename) is never re-embedded — its vector goes permanently stale

- 位置：`service/build_notes_db.py:87`
- 状态：✅ 已确认（双票通过对抗验证）
- 细节：load_ledger stores filenames; line 87 `to_process = [f for f in all_notes if f not in processed]` and lines 118/149 append the filename to the ledger. ### [MEDIUM] A PDF group is recorded as fully processed if ANY file in it produced chunks, so a per-file extraction failure silently leaves the group partially ingested and never retried

- 位置：`service/build_pdf_db.py:302`

## 维度：core scanner pipeline logic

> The pipeline's architecture is genuinely well designed — clean 2-stage routing, a pure renderer, an atomic dedup ledger, careful UTF-8 hygiene, and a thoughtful manifest/resume protocol for the zero-API backend — but the shipped code cannot currently run at all: gemini_analyze_pdf.py lost its `if __name__ == \"__main__\"` guard (the `main()` call sits unreachable inside main's own body), so the core script is a silent exit-0 no-op that the batch scanner reports as success. Beyond that showstopper, the ledger contract is split across two default file paths (writer vs. readers), and the publish/post-publish sequencing has several money-burning or silently-wrong paths: --out-dir under the default vault target crashes post-publish after paid generation, the default post-publish actions invoke scripts that don't ship with the repo, and the subagent resume state machine has three holes (stale-output reuse defeating --force, schema-invalid outputs wedging a run invisibly, and no run_dir↔PDF-set validation). The fixes are mostly small and localized; the design itself is sound.

### [CRITICAL] The per-paper pipeline script has no entry point — running it directly is a silent no-op that exits 0, and the batch scanner counts every group as Success.

- 位置：`scanner/gemini_analyze_pdf.py:1841`
- 状态：✅ 已确认（双票通过对抗验证）
- 细节：The file ends with:
```
    except Exception:
        ...
        raise

    main()
```
The final `    main()` (line 1841) is indented 4 spaces, making it the last statement *inside* `def main():` (line 1610) — and it is unreachable because every path before it returns, raises, or calls sys.exit. There is no module-level `if __name__ == "__main__": main()` (AST-verified: the module's top-level body contains only imports/assignments/FunctionDefs, no call). Consequence: `python scanner/gemini_analyze_pdf.py paper.pdf` defines functions and exits 0 without doing anything. zotero_batch_scanner.process_group (line 656: `if completed.returncode == 0: return True`) then reports "Result Group N: Success" for every paper while no note is generated, no manifest is written, and no ledger entry is made — total silent pipeline no-op with an all-green report. The stray call dates to the initial public release commit (c07715b), so the published repo has never had a working CLI entry point for its core script.

## 维度：LLM backend contract consistency

> The backend abstraction itself is well designed: a clean two-method contract (attach_pdfs/call_model), a centralized env-resolving factory, matched pending-detection invariants between subagent.py and list_pending_subagent_runs.py, no API keys logged or written into manifests/run artifacts, and a schema_version-3 manifest that matches what the helper and host-contract doc consume. The critical fragility is that the contract's `schema` parameter is de facto Vertex-dialect (uppercase types, propertyOrdering, nullable) while the Anthropic and OpenAI backends forward it verbatim to APIs that require standard JSON Schema — making two of the five advertised backends nonfunctional with the shipped domain packs, untested because no test exercises call_model. Secondary weaknesses cluster on the error paths: no backend inspects stop/finish reasons so truncated or blocked output crashes with misleading errors (then gets retried at full cost), and the zero-API subagent path has a doc-vs-code auto-resume contradiction that can deadlock a literal-minded parent agent plus a resume_command that is only executable from the repo root on machines where `python` exists.

### [HIGH] Uncommented $HOME defaults in .env.example silently break on Windows because HOME is not a Windows environment variable

- 位置：`.env.example:12`
- 状态：⬜ 未验证（验证阶段随工作流中止）
- 细节：The four active (uncommented) path lines use `$HOME`: `LOCALRAG_NOTES_DIR=$HOME/research-note` (L12), `LOCALRAG_HOME=$HOME/.localrag` (L15), `ZOTERO_DB_PATH=$HOME/Zotero/zotero.sqlite` (L29), `ZOTERO_DATA_DIR=$HOME/Zotero` (L30). The file header (L4) tells users to "Copy this file to `.env`". Both `scanner/config.py:_env_path` and `service/config.py:_env_path` resolve values via `os.path.expandvars(os.path.expanduser(raw))` — but on Windows, `HOME` is not defined in cmd/PowerShell (verified on this machine: `os.environ.get("HOME")` is `None`, and `os.path.expandvars("$HOME/research-note")` returns the literal string). Result: `VAULT_ROOT`, `LOCALRAG_HOME`, and the Chroma/ledger paths become the RELATIVE path `$HOME\research-note` under whatever cwd the script runs from — notes and the vector DB land in `<cwd>\$HOME\...` and silently move when cwd changes, so a Windows user's query server reads an empty DB. README explicitly supports Windows (`setup.ps1`, `.venv\Scripts\python.exe` instructions) and CI runs windows-latest. Fix: use `~/research-note` style defaults (expanduser is cross-platform, and `.claude-plugin/plugin.json` already uses `~/...` correctly), and make init_environment.py default to `str(Path.home())`-based paths instead of echoing the raw env value.
